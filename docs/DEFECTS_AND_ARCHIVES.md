# 缺陷、审计、用例套件与快照归档

## 本阶段要解决什么

这一阶段把原有的“项目 → 用例 → 计划 → 执行”扩展成更接近真实 QA 工作的两个闭环：

```text
测试执行失败
  → 提交缺陷并关联项目/用例/执行
  → 分配负责人
  → 处理、解决、验证、关闭或重新打开
  → 查看每次变更的审计历史

用例持续维护
  → 按业务层级放入用例套件
  → 在版本/里程碑节点生成快照
  → 后续修改源用例
  → 历史快照仍然保留当时的内容
```

所有数据仍只写入本机 `backend/.data/qa.db`。这一阶段不连接 Jira、TAPD、公司数据库、对象存储或任何真实业务 API。

## 页面与 API 入口

启动后端与前端后，使用以下入口：

- 缺陷管理页：`http://127.0.0.1:5173/defects`
- 用例套件与快照页：`http://127.0.0.1:5173/test-suites`
- Swagger/OpenAPI：`http://127.0.0.1:23100/docs`
- 业务 API 前缀：`http://127.0.0.1:23100/api/v1`

缺陷页支持创建、编辑、筛选、状态流转、关联用例/执行和查看审计时间线。用例套件页支持建立层级、编辑、归档、安全删除和按项目/套件生成快照。

## 缺陷单学习模型

一条缺陷包含：

- 必填项目、标题和报告人。
- 严重程度：`blocker` / `critical` / `major` / `minor` / `trivial`。
- 处理优先级：`P0` / `P1` / `P2` / `P3`。
- 负责人、测试环境、复现步骤、预期结果、实际结果和解决说明。
- 可选关联测试用例和测试执行，关联对象必须属于同一项目。

严重程度回答“影响多大”，优先级回答“多快处理”。它们不是同一个维度：一个影响很大但暂时没有发布路径的问题，可以是高严重程度、较低处理优先级。

### 状态机

```text
open ──→ in_progress ──→ resolved ──→ verified ──→ closed
  └─────────────────→ resolved
in_progress ──→ open
resolved/verified/closed ──→ reopened ──→ in_progress 或 resolved
```

关键业务规则：

- 进入 `in_progress` 前必须指定负责人。
- 进入 `resolved` 时必须填解决说明。
- 进入 `reopened` 时必须填重开原因，并清理上一次解决/关闭时间。
- 已关闭缺陷不能普通编辑，只能按规则重新打开。
- 不提供缺陷物理删除，历史问题通过 `closed` 表达结束。
- 项目存在未关闭缺陷时不能归档；已被缺陷引用的用例或执行不能直接删除。

这些规则的学习价值是：把前端按钮、HTTP 接口、Service 校验、领域状态机、Repository 持久化和自动化测试串成一个完整业务用例。

## 审计历史

审计事件是追加式记录，当前覆盖：

- 缺陷的创建、字段更新和状态流转。
- 用例套件的创建、更新、状态流转和删除。
- 用例快照的创建。

每条事件保存业务对象类型和编号、动作、变更前/后值、备注、操作人和时间。对外只提供 `GET /api/v1/audit-events`，没有修改或删除审计事件的 API。

### 必须明确的边界

这是业务教学审计，不是合规级审计：

- `actor` 现在来自经过 Session 认证的本机用户，并保存可查询的用户关联；但它仍不是企业 SSO 或不可抵赖身份。
- 没有数字签名、哈希链、WORM 存储、独立备份、保留策略或管理员职责分离。
- 业务记录与审计记录通过不同 Repository 分别提交，目前不是原子 Unit of Work。
- 单进程业务锁只解决本机并发教学问题，不能替代多实例数据库事务。

后续的正确演进方向是：引入 Unit of Work/outbox、数据库约束与并发版本、审计保留策略，再根据公司合规要求评估独立、不可篡改的专用存储。

## 用例套件

用例套件用来表达业务目录，例如：

```text
角色系统
├── 创角
│   ├── 外观
│   └── 职业与初始数值
└── 成长
    ├── 升级
    └── 技能
```

已实现的规则：

- 套件可以嵌套，但必须属于同一项目，且不能形成循环。
- 同一父节点下的套件名不能重复。
- 套件有 `active` 和 `archived` 两种状态，已归档套件不再接收新的用例归属。
- 套件存在子套件或关联用例时不能删除。
- 用例的 `suite_id` 是可选的，允许先建用例、后整理目录。

学习重点不只是“显示一棵树”，而是实现父子关系、同项目校验、循环检测、归档语义与安全删除约束。

## 不可变用例快照

快照可以按整个项目，或按一个套件范围生成。套件快照可以选择是否包含所有后代套件。系统会冻结：

- 快照范围、名称、递增版本和用例数量。
- 源用例/套件 ID 和当时的套件路径。
- 用例标题、前置条件、步骤、优先级、类型、状态、标签和源时间。

快照没有更新和删除 API。创建后，源用例的后续更改不会修改已有快照。如果要保留一个新节点，应创建下一版快照，而不是覆盖旧版。

这里学到的是“可编辑当前状态”与“不可变历史事实”两种建模方式的区别。后续做发布基线、用例审批、合规报告或质量趋势时，这个区别非常关键。

## 建议的本地学习步骤

1. 创建一个活跃项目，建立两层用例套件。
2. 创建三条用例，将其中两条放入不同的套件，一条保持未归类。
3. 创建项目快照 `baseline-1`，记住快照的版本和用例内容。
4. 修改一条源用例，重新打开 `baseline-1`，确认其仍是修改前的内容。
5. 创建 `baseline-2`，比较两个快照的版本与内容。
6. 创建计划和执行，将一条用例记为失败。
7. 从缺陷页创建缺陷，关联这条用例和执行，完整填写环境、复现步骤、预期与实际结果。
8. 尝试在没有负责人时进入处理中，观察业务校验；指定负责人后再流转。
9. 依次执行解决、验证和关闭，查看审计时间线里的字段差异和备注。
10. 重新打开缺陷，确认必须填原因，并观察解决/关闭时间被清理。
11. 在 Swagger 中重复一遍上述过程，对照请求、统一响应、HTTP 状态码和错误信息。
12. 在缺陷下添加评论并上传一张虚构截图，验证作者权限、软删除和附件安全检查。
13. 阅读对应的 API/Service/Repository/迁移/测试文件，画出一次请求从前端到 SQLite 的调用链。

## 已实现与未实现边界

| 能力 | 当前状态 | 后续演进 |
| --- | --- | --- |
| 缺陷表单与状态机 | 已实现本地创建、查询、编辑与流转闭环 | 批量操作、通知、SLA 和外部缺陷同步 |
| 缺陷与用例/执行关联 | 已实现同项目校验及失败/阻塞结果带上下文提单 | 缺陷反向链接、批量关联和版本维度 |
| 评论与附件 | 已实现目标关联、回复、作者权限、安全本机附件和图片重编码 | 对象存储、恶意文件扫描、通知和内容治理 |
| 审计历史 | 已绑定登录主体并记录追加式业务事件 | Unit of Work、防篡改和保留策略 |
| 树形用例套件 | 已实现层级、循环检测和归档 | 拖拽排序、批量移动、项目级权限和评审 |
| 用例快照 | 已实现项目/套件范围的不可变版本 | 快照 diff、基线审批和发布关联 |
| Excel/CSV | 已实现用例/缺陷模板、预检、错误行、摘要确认、部分创建与导出 | 业务幂等键、异步大文件、原子 Unit of Work |
| 外部缺陷 API | 未实现且默认禁用 | 完成本地边界后再做 Jira/TAPD Provider |

Excel/CSV 导入现在仍通过现有 Service 业务规则逐行创建，不会绕过状态与关联校验。默认 clean gate 在预检有错误时零写入；显式允许部分导入后不是整批事务，成功行不会因后续失败自动回滚。这个边界必须在 UI 和 API 结果中保持可见。

## 本阶段验收点

1. 重启后端后套件、快照、缺陷和审计事件仍在。
2. 套件不能跨项目挂载、形成循环或在存在引用时删除。
3. 修改源用例后旧快照不变，新快照按范围递增版本。
4. 缺陷只能沿允许的状态路径流转，必要的负责人、解决说明和重开原因会被校验。
5. 缺陷不能关联其他项目的用例或执行。
6. 变更后可查询对应的审计事件和字段差异。
7. 说明文档能清楚回答“已实现什么”、“为什么这样建模”和“距离企业生产系统还差什么”。
