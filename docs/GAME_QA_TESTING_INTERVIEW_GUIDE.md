# 游戏 QA 测试方法与面试手册

这份手册用于两件事：一是指导游戏 QA 实际开展测试，二是帮助面试时把“测了什么、
为什么这样测、数据从哪里来、如何判定”说完整。它覆盖功能、战斗数值、关卡任务、
接口、兼容、图形、性能、温度稳定性、弱网联机、配置表、Excel/Lua、自动化、CI/CD
和发布质量门禁。

> 重要：文中的数值分为硬约束、项目阈值和实验室示例。除明确标为硬约束的项目外，
> 示例值不能直接冒充行业标准。正式项目必须结合目标帧率、机型档位、场景、画质、
> 构建类型、样本量和历史基线确定阈值。

## 1. 面试先讲清楚的总框架

### 1.1 一条完整 QA 闭环

```text
需求/版本变更
  → 风险分析与测试矩阵
  → 用例设计、评审和数据准备
  → 环境确认与冒烟
  → 功能、专项、兼容和性能执行
  → 缺陷、日志、截图、指标与请求链路留证
  → 修复验证与影响面回归
  → 发布准入
  → 线上观察和复盘沉淀
```

面试时不要只回答“点了哪些按钮”。一个成熟回答至少包含：

1. 测试目标与最大风险；
2. 覆盖维度和优先级；
3. 环境、账号、数据和基线；
4. 操作流程与自动化方式；
5. 原始数据、统计口径与通过标准；
6. 发现的问题、定位证据、回归范围和最终结果。

可以使用这个 60 秒句式：

> 这个模块的核心风险是 **X**。我按 **功能路径 × 状态 × 数据边界 × 网络 × 设备**
> 建矩阵，先跑主链路冒烟，再覆盖异常和专项。执行时采集 **客户端日志、服务端请求链、
> 数据快照和性能指标**，按需求硬约束、机型预算及历史基线判定。发现异常后用
> **request_id、时间戳和最小复现步骤**定位，修复后回归直接影响面与公共依赖，最后把
> 用例、缺陷和质量门禁沉淀到平台与 CI 中。

### 1.2 阈值的三层口径

| 层级 | 含义 | 例子 |
| --- | --- | --- |
| 硬约束 | 业务正确性或安全底线，通常零容忍 | 崩溃、丢档、越权、重复扣款、重复发奖、配置主键重复 |
| 项目阈值 | 产品、技术预算和目标设备共同约定 | 目标 FPS、PSS 上限、首包时间、重连时间、包体大小 |
| 统计基线 | 与同条件的稳定版本比较 | FPS 回退、内存增长、加载耗时回退、崩溃率变化 |

“上限/下限”不只是一个数字，还必须带条件：

```text
指标 + 统计口径 + 场景 + 设备档位 + 画质 + 构建类型
+ 冷/热启动 + 持续时间 + 样本量 + 基线版本
```

例如“FPS 不低于 55”不完整；更好的说法是：

> 高端 Android、正式包、默认高画质、同一战斗回放，预热 3 分钟后采 10 分钟，
> 重复 3 次取中位数；目标 60 FPS，平均 FPS 不低于 55，P95 帧时间不高于 20 ms，
> 并且相对基线不回退超过 5%。这些是该项目的验收值，不是通用标准。

### 1.3 所有测试都应保存的运行元数据

至少保存以下字段，才能复现和比较：

- 需求、用例、缺陷、构建号、代码/配置版本和资源版本；
- 平台、设备型号、OS、CPU/GPU、内存、分辨率、DPI、驱动或图形 API；
- 服务器环境、区服、账号、角色、网络配置和时间同步状态；
- 画质、帧率档、语言、渠道、安装方式、冷/热启动；
- 场景、操作脚本、开始/结束时间、采样周期和运行次数；
- 原始日志、截图/视频、抓包、性能原始文件、导出报表和工具版本。

### 1.4 测试类型速查图

| 类型 | 核心问题 | 最重要的判定 |
| --- | --- | --- |
| 功能/系统 | 状态和业务结果是否正确 | 需求约束、状态机、最终数据一致 |
| 战斗/数值/AI | 公式、时序和权威结算是否正确 | 可复算、边界正确、非法输入不生效 |
| 关卡/任务/资源 | 路径、触发、进度和资产是否可用 | 无阻断、无死链、关键资源完整 |
| API/异步 HTTP | 契约、并发、超时和副作用是否可靠 | 幂等、终态收敛、异常可恢复 |
| 弱网/联机 | 网络恶化后能否提示、恢复和对账 | 无重复副作用、重连成功、状态收敛 |
| 兼容/图形 | 设备、系统和渲染组合是否正常 | 无 Crash/黑屏/致命伪影，矩阵达标 |
| 安装/升级 | 版本切换和数据迁移是否安全 | 数据不丢、文件一致、失败可恢复 |
| 性能/热力 | 是否达到帧预算并能定位热区 | P95/P99、低帧占比、相对基线 |
| 温度/功耗/稳定性 | 长时间运行是否衰减或泄漏 | 无 Crash/ANR/OOM、无持续增长 |
| 配置表/Lua | 表结构、数值关系和制品是否可信 | Schema 全过、生成确定、hash 可追溯 |
| 用例/缺陷/审计 | 测试资产和问题是否可追溯 | 快照不变、证据完整、审计追加 |
| 冒烟/回归/发布 | 当前版本是否可以继续或发布 | 关键用例 100%、阻断问题为 0 |
| 自动化/CI/CD | 验证是否稳定、可重复、可门禁 | 制品可信、Secret 安全、失败可恢复 |

## 2. 数据怎样提取和计算

### 2.1 常用证据源

| 证据源 | 能回答的问题 | 常见取得方式 |
| --- | --- | --- |
| 客户端日志 | 操作、状态机、资源加载、异常栈、网络错误 | 游戏日志、设备日志、崩溃文件，统一带时间戳 |
| 服务端日志 | 请求是否到达、业务校验、数据库/缓存结果 | request_id、user_id、session/room、错误码和耗时 |
| HTTP/协议轨迹 | 请求顺序、重试、超时、重复包、状态码 | 代理、抓包、SDK 拦截器；脱敏后保存 |
| 数据快照 | 扣除、发放、库存、进度是否一致 | 测试 API、只读查询、前后端导出；不直接改线上库 |
| 性能采样 | FPS、帧时间、CPU/GPU、内存、温度、功耗 | 平台 profiler、设备工具、引擎 stat/trace、项目采集器 |
| 图像/视频 | 花屏、布局、渲染、时序、复现过程 | 截图、录屏、基线图与差异图 |
| 配置制品 | 表结构、数值、版本和生成结果 | Excel/CSV、Schema、Lua/JSON、hash 和差异报告 |
| CI 制品 | 构建、测试、覆盖、门禁和发布证据 | 测试报告、日志、Artifact、审批和审计记录 |

数据链路要做三件事：所有设备校时；用同一个运行 ID 串联各端；原始数据只追加保存，
统计结果可以重新生成。

### 2.2 高频统计公式

```text
通过率       = 通过用例数 / 已执行用例数 × 100%
缺陷逃逸率   = 发布后发现缺陷数 / 发布前后发现缺陷总数 × 100%
回归变化率   = (新版本值 - 基线值) / 基线值 × 100%
平均 FPS     = 有效采样 FPS 之和 / 样本数
帧预算       = 1000 / 目标 FPS（毫秒）
内存增长斜率 = (结束 PSS - 开始 PSS) / 运行时间
吞吐率       = 时间窗内成功请求数 / 时间窗长度
网络速率     = 字节增量 × 8 / 时间增量
```

P95/P99 要基于原始样本排序计算，不能用平均值代替。对有预热、随机和设备抖动的指标，
建议同条件至少运行 3 次，报告中位数、P95/P99、最大值和失败样本；正式容量测试的样本量
应根据置信区间另行设计。

## 3. 功能与系统测试

### 3.1 通用功能测试

**测什么**

- 正常主链路、分支、取消、返回、重复操作和中断恢复；
- 输入等价类、边界值、空值、非法值、超长、多语言和特殊字符；
- 不同角色、权限、生命周期和前置状态；
- 跨系统数据一致性、重复提交、并发操作和失败补偿。

**流程**

1. 从验收条件抽取状态、输入、输出和依赖；
2. 用“功能 × 状态 × 数据 × 权限 × 环境”建立矩阵；
3. 正向主链路后测试边界、异常、并发和恢复；
4. 比较 UI、客户端状态、接口响应和权威数据源；
5. 关联缺陷，修复后回归直接影响面、公共组件和历史高风险路径。

**数据与上下限**

- 必填、类型、长度、枚举、唯一性和状态转换按需求精确判断；
- 数字边界使用 `min-1、min、min+1、max-1、max、max+1`；
- 对不允许重复执行的业务，最终副作用必须恰好 1 次；
- 未授权成功、负库存、丢数据和状态机非法跳转为 0 容忍；
- UI 提示和接口错误码应稳定、可理解且不能泄漏内部敏感信息。

**面试回答重点**：我不只验证界面结果，而是同时验证状态机、接口副作用和持久化结果。

### 3.2 账号、登录、角色与权限

覆盖注册/游客、登录、登出、Token/Session 过期、顶号、多端、封禁、注销、找回、角色创建、
跨区服和 RBAC。依次验证正确凭据、错误凭据、锁定、过期、刷新、撤权后旧会话和并发登录。

采集登录接口状态码、错误码、认证事件、Session 创建/失效时间和权限审计。硬标准是未授权访问
成功数为 0，注销/撤权后的会话不能继续执行受保护写操作；失败次数、锁定时长和会话有效期
属于安全策略，不应由测试人员凭经验拍值。

### 3.3 背包、商店、邮件、抽卡和经济系统

核心是“账要守恒、操作可追溯、重复请求不重复生效”。

```text
期望余额 = 操作前余额 + 合法发放 - 合法扣除
期望库存 = 操作前库存 + 获得数量 - 消耗数量
```

流程要覆盖余额刚好够/差 1/为 0/达到容量上限、批量购买、折扣、限购刷新、过期邮件、满背包、
断网重试、双端并发和服务重启恢复。采集操作前后快照、订单号、幂等键、流水、奖励明细和回调次数。

硬标准：余额和库存不应无业务理由变负；同一订单扣款和发货各恰好一次；失败事务不应出现只扣不发
或只发不记账。抽卡概率要用足够样本做二项分布/卡方检验，并结合保底状态机验证；单次结果不能用来
证明概率错误，容差和置信水平由设计与统计方案确定。

### 3.4 支付测试

覆盖下单、渠道支付、回调、补单、退款、取消、超时、重复回调、乱序回调、金额/币种篡改和账号不一致。
用唯一订单号串起客户端、游戏服和支付模拟器，保存每次状态转换和账务快照。

发布阻断项包括：重复扣款、重复发货、金额校验绕过、订单串号、退款后权益未按规则回收。真实支付环境
必须使用公司批准的沙箱和脱敏测试账号；本学习项目只应使用自建模拟服务。

### 3.5 社交、邮件、公会和排行榜

覆盖添加/删除/拉黑、双向状态、离线消息、重复消息、群组权限、公会职位、跨天结算、并列排名和奖励发放。
采集发送端/接收端事件 ID、消息序列号、已读游标、排行榜快照和结算批次。硬标准是权限越界为 0，
同一结算批次奖励恰好一次；实时可见延迟和榜单刷新周期按产品约定。

### 3.6 活动、时间和时区

至少测 `开始前 1 秒、开始时、开始后 1 秒、结束前 1 秒、结束时、结束后 1 秒`，再覆盖跨天、跨周、
月末、闰日、夏令时、客户端改时钟、服务端时钟漂移、补偿和重复结算。权威时间应来自服务端。

采集服务端时间、活动配置版本、时区、结算批次和奖励流水。活动窗口不能重叠时，重叠数必须为 0；
开始时间必须小于结束时间；结算和奖励幂等。

### 3.7 UI、易用性、本地化和可访问性

检查视觉还原、遮挡、截断、滚动、键鼠/手柄/触控、焦点、返回键、刘海/安全区、字号、色盲提示、
多语言膨胀、复数/性别、日期货币和 RTL 布局。保存分辨率、DPI、语言、主题、字体、截图和交互视频。

文本截断、关键按钮不可达、关键状态只靠颜色表达等按严重程度处理；像素容差只能用于稳定区域，动态时间、
粒子和反锯齿区域应遮罩。视觉自动对比的实验室参考可以是 `SSIM ≥ 0.98` 或差异像素率
`≤ 0.1%～1%`，但必须先固定字体、分辨率、渲染设置和遮罩，最终仍需人工确认。

## 4. 战斗、数值与 AI 测试

### 4.1 战斗测试

**测什么**

- 普攻、技能、连招、冷却、消耗、打断、霸体、无敌、死亡和复活；
- 伤害、治疗、暴击、命中、闪避、防御、元素、距离和阵营；
- Buff/Debuff 的叠加、刷新、覆盖、驱散、免疫、持续时间和结算顺序；
- 客户端表现、服务端权威结果、战斗日志和结算奖励的一致性；
- 多人同步、作弊输入、极端帧率和弱网下的状态收敛。

**流程**

1. 把策划公式拆成输入、固定系数、随机项、取整点和结算顺序；
2. 构造单变量可控场景，固定随机种子或关闭随机；
3. 先测单技能，再测组合、打断、边界和多人并发；
4. 用独立 Oracle 计算期望值，和服务端战斗日志逐步比对；
5. 对差异定位到输入、公式、取整、时序、同步或表现层。

**数值边界**

- HP/资源：0、1、上限-1、上限、溢出、负增益和同时归零；
- 距离/角度：判定边界内外各一点；
- 时间：冷却和 Buff 到期前后一个 tick/frame；
- 层数：0、1、最大层、最大层+1；
- 概率：0%、接近 0、50%、接近 100%、100%；
- 数据类型：32 位/64 位极值、浮点精度、NaN/Infinity 输入拒绝。

整数和货币类结果应精确相等；浮点比较使用领域定义的 `epsilon`，并明确先乘后加、取整方式和取整位置。
服务器权威战斗中，非法伤害、越界技能和重复结算成功数必须为 0。

### 4.2 AI 与关卡内行为

覆盖感知距离、仇恨、寻路、脱战、技能选择、目标丢失、卡死、多人争抢、障碍动态变化和不同难度。
采集 AI 状态转换、导航路径、目标 ID、技能决策、位置、速度、卡住时长和服务器 tick。

通过标准不能只写“看起来正常”：例如 AI 不进入非法状态；不可达时能在项目规定时间内重规划；
没有长时间原地抖动；相同种子和输入下结果可解释。距离、超时和路径偏差阈值由关卡/战斗设计给出。

**面试回答重点**：数值测试不是“多打一遍”，而是建立可复算的公式 Oracle，并控制随机、取整和时序。

## 5. 关卡、任务与资源测试

### 5.1 关卡和开放世界

覆盖出生点、边界、空气墙、碰撞、坡度、跳跃、载具、传送、存档点、流式加载、重生、断线回归和多人位置。
遍历主路径、分支、逆向、极限速度和边界穿越；把路径轨迹叠加在地图上，标记卡点、跌落、加载停顿和
低 FPS 热区。

采集位置 `x/y/z`、旋转、关卡/区域 ID、时间戳、移动模式、加载事件、FPS、draw call 和资源加载日志。
硬标准是主流程不可阻断、关键区域不可永久卡死、不可越过安全/付费边界；可接受碰撞缝隙和加载耗时
按地图规范及设备档位定义。

### 5.2 任务系统

覆盖接取条件、步骤顺序、并行/互斥、计数、共享进度、放弃、重接、失败、断线、跨天、版本迁移和奖励。
用任务状态机逐边测试，并比较事件流、进度快照和奖励流水。

前置条件缺失时不能接取；计数不应回退或重复累计；完成和领奖必须幂等；死链、循环依赖和不可达状态为 0。

### 5.3 资源、模型、动画、音频和特效

检查资源缺失、引用、命名、压缩、LOD、材质、贴图、骨骼、碰撞、动画状态、音画同步、粒子数量和内存占用。
在各画质和目标平台加载/卸载，进行快速切换、重复进入和长时间循环；采集加载日志、资源路径、包大小、
显存/内存、渲染统计和截图。

缺失资源、粉色材质、致命引用和关键动作错位通常零容忍；LOD 距离、贴图预算、音频响度和粒子预算由项目规范定义。

## 6. API、异步 HTTP、协议与安全测试

### 6.1 API 功能和契约

对每个接口覆盖方法、路径、Header、鉴权、Schema、类型、空值、边界、错误码、分页、排序、并发和版本兼容。
先按 OpenAPI/协议定义生成正常请求，再做字段缺失、额外字段、类型错、越权和状态不允许。

保存请求 ID、去敏请求摘要、状态码、业务码、响应 Schema、耗时、重试次数和服务端链路。成功/失败语义必须稳定，
未知字段策略和向后兼容策略要明确。

### 6.2 异步 HTTP 专项

重点验证以下机制，而不只是“能请求成功”：

- 连接、读取、写入和连接池超时分别生效；
- 并发上限和连接复用，不因无限创建任务耗尽连接；
- 取消能够向下传播并释放资源；
- 只对安全或有幂等键的操作重试，使用有界次数和退避；
- `202 Accepted` 后通过轮询/Webhook 收敛到终态；
- 相同幂等键同输入返回同一结果，不同输入发生冲突；
- 乱序、重复、延迟 Webhook 不让终态回退；
- 服务重启后任务状态可恢复，超时和异常映射对调用方稳定。

数据提取包括客户端分阶段耗时、连接池指标、任务数、状态变化时间线、幂等记录、Webhook sequence 和服务端日志。
硬标准是非幂等副作用不重复、取消后无孤儿任务、终态不倒退。超时、重试次数和并发量按依赖 SLA 与容量实验确定。

### 6.3 接口性能

从峰值在线、每用户操作频率和安全系数推导目标吞吐，不直接套一个 QPS：

```text
目标 QPS ≈ 峰值活跃用户 × 单用户每秒请求数 × 1.5～2 安全系数
```

在目标负载下报告成功率、业务错误率、P50/P95/P99、吞吐、连接数、CPU/内存和下游耗时。
实验室可先用“服务端错误率 <0.1%、内部轻量读接口 P95 <200～500 ms、无持续资源增长”作练习值，
但正式门槛必须来自接口 SLO；支付、匹配和大查询不能共用同一耗时阈值。

### 6.4 安全和非法协议

覆盖未认证、越权访问、对象 ID 替换、重放、签名过期、参数篡改、注入、上传文件、敏感日志、限流和 Secret 泄漏。
采集安全审计、错误码、签名校验原因、访问主体和资源 ID。

越权成功、密钥写入仓库/日志、任意文件访问、客户端可决定权威数值均为 0 容忍。安全测试只能在已授权的隔离环境进行。

## 7. 弱网、断网与多人同步测试

### 7.1 弱网不等于“看流量”

网络测试至少要控制和记录：上下行带宽、延迟、抖动、丢包、乱序/重复、断网方向和网络切换。
只采集发送/接收字节和包数量，能说明流量，却不能证明已经做了弱网注入。

### 7.2 自建实验室网络档位示例

| 档位 | RTT/延迟参考 | 抖动 | 丢包 | 下行/上行参考 | 用途 |
| --- | --- | --- | --- | --- | --- |
| 基线 Wi-Fi | 20～50 ms | ≤10 ms | ≤0.5% | ≥10 Mbps / ≥5 Mbps | 建立正常基线 |
| 良好移动网 | 50～100 ms | 10～30 ms | ≤1% | 5～20 / 1～5 Mbps | 日常移动网络 |
| 弱网 | 100～200 ms | 30～80 ms | 1%～3% | 1～5 Mbps / 256 Kbps～1 Mbps | 重试、提示和同步 |
| 严重弱网 | 200～500 ms | 80～150 ms | 3%～10% | 256 Kbps～1 Mbps / 128～512 Kbps | 降级与恢复 |
| 断网/黑洞 | 无响应 | 不适用 | 100% 或单向 | 0 | 超时、取消、重连 |

这些仅是实验室 Profile 示例。实际值应参考目标市场运营商采样；注入工具需要确认参数是单向延迟还是 RTT。

### 7.3 测试流程

1. 基线网络跑同一脚本并校时；
2. 分别注入上/下行带宽、延迟、抖动和丢包，避免一次改变所有变量；
3. 在登录、下载、战斗、匹配、聊天、结算、支付等关键阶段切网/断网；
4. 测 Wi-Fi 与移动网切换、前后台、IP 变化、单向黑洞和服务端重启；
5. 恢复网络，验证重连、补偿、状态对账和幂等；
6. 对照抓包、客户端日志、服务端序列号和最终数据快照。

采集 `request_id/session/room_id/sequence`、客户端发送/确认时间、RTT、重传、丢包、重连次数、
断线检测时间、恢复时间和恢复前后状态。流量按字节增量计算，不能拿累计值当瞬时速率。

自建实验室可以在 Linux 网关使用 `tc netem`，HTTP/TCP 使用 Toxiproxy 或自建代理，Windows 使用受控的
WinDivert 类注入工具，移动设备则统一经过受控路由器。普通 HTTP 代理不能完整模拟 UDP 游戏协议。
注入前后要用探测或抓包确认真实 RTT、单向延迟和丢包，不能只相信工具配置框中的数字。

**通过标准**

- 没有无限 loading，超时提示明确，重试有界并退避；
- 登录、匹配、战斗和结算最终状态可收敛；
- 不重复扣除/发奖/创建角色或订单；
- 断线重连后位置、HP、背包、任务和结算以权威状态对账；
- 实验室可先设置关键会话重连 `≤5～10 秒`、状态在 `1～3` 个快照周期内收敛，
  但正式值由玩法可接受中断和服务端协议确定。

### 7.4 多人同步

覆盖加入/离开、房主迁移、帧同步/状态同步、迟到包、重复包、乱序包、预测回滚、观战和中途加入。
采集 tick/帧号、输入序列、权威快照、客户端位置/HP、校正次数和回滚长度。

位置误差、命中确认时间和可接受回滚帧数必须由玩法设计按单位、速度和镜头感受确定；不能把另一款游戏的米数直接套用。

**面试回答重点**：我会把“网络注入参数—客户端表现—协议时序—服务端权威状态”四层证据对齐。

## 8. 兼容、安装升级与图形测试

### 8.1 设备兼容矩阵

按风险而不是只按设备数量选型：

- 平台与 OS：最低支持、主流、最新、升级路径；
- 芯片与 GPU：厂商、架构、驱动和高中低档；
- 内存/存储：最低配置、常见配置、低剩余空间；
- 屏幕：分辨率、比例、DPI、刷新率、刘海、折叠屏、横竖屏；
- 图形：OpenGL/Vulkan/Metal/DirectX、画质、HDR、抗锯齿和超分辨率；
- 输入与外设：触屏、键鼠、手柄、音频和权限。

每台设备保存机型、OS、CPU/GPU、内存、分辨率/DPI、图形 API/驱动、刷新率、包体和配置版本。
关键路径崩溃、黑屏、花屏、无法安装/启动为 0 容忍。设备覆盖率应按目标用户占比或风险权重计算，
不能只报“测了 20 台”。

常见取数入口：Android 用 `getprop`、`dumpsys package/meminfo/gfxinfo`、logcat 和 Perfetto；iOS 用 Xcode Devices、
Instruments、MetricKit 和 WDA；Windows 用 dxdiag/WMI、PresentMon、ETW、PIX/RenderDoc、事件日志和 Dump。
工具名称不是重点，重点是把硬件/驱动环境指纹、画面证据、崩溃栈和同一时段的性能曲线关联起来。

### 8.2 安装、升级和补丁

覆盖全新安装、覆盖安装、跨多个历史版本升级、资源热更、补丁中断/恢复、空间不足、权限拒绝、降级、卸载重装、
存档保留和校验失败。保存安装器日志、包/补丁 hash、前后版本、磁盘变化、耗时和数据迁移记录。

通过标准：签名和完整性校验正确；失败可恢复或明确回滚；升级后账号、设置和存档按规则保留；不能进入半新半旧状态。
磁盘最低空间、下载时间和包体上限由渠道与项目预算定义。

建议保存 `source_version、target_version、package/patch/manifest_hash、exit_code、download_bytes、resume_offset、
temporary/final_disk_bytes、retry_count、migration_version、rollback_result`。如果安装器计算需要空间为 `R`，
应至少测试 `R-1 MB、R、R+20%`，并在下载 10%、50%、99%、校验、解压、文件切换和数据迁移阶段分别中断。
P0 设备的新装和主升级路径通常要求 100% 通过，文件 hash 不一致、存档/货币丢失和不可恢复状态为 0。

### 8.3 图形兼容

建立固定图形地图/回放，分别覆盖贴花、烘焙光、方向光、点光、渲染管线、材质、阴影、透明、粒子、后处理和 UI。
在各图形 API、画质和超分模式运行，固定镜头截图/录屏，同时收集渲染日志、GPU/驱动和崩溃文件。

超分辨率至少覆盖关闭和每个质量档。例如 PC 可按项目支持的 DLSS、FSR、XeSS 档位，移动端按 Mobile FSR/GSR 档位
建立组合；不支持的设备要得到“受控降级”，而不是崩溃或黑屏。

自动视觉对比可使用固定基线、mask、像素差异率或 SSIM，但动画、粒子、时间、反锯齿和驱动微差需要容差与人工复核。
严重伪影、关键对象缺失、黑屏和崩溃零容忍；轻微像素差异使用项目基线阈值。

### 8.4 本项目规划边界

当前学习项目尚未实现设备截图采集和自动视觉回归。后续若自行实现，应为每次运行保存基线 ID、分辨率/DPI、
OS/驱动/RHI、图片 hash、遮罩、像素差异、阈值和人工复核结论。完成代码、自动化测试和真实设备验证前，
只能表述为“已设计图形兼容测试方法”，不能表述为已完成自动图像判定。

## 9. 性能、场景热力、温度与稳定性

### 9.1 场景和步骤

至少建立以下可重复脚本：冷/热启动、登录、主城/开放世界移动、密集战斗、多人同屏、重 UI、资源快速切换、
后台恢复、充电/低电量和 1～8 小时稳定性循环。先预热，再固定路线、角色、镜头、画质和网络，多次运行。

### 9.2 指标和取数

| 领域 | 原始指标 | 重点统计 |
| --- | --- | --- |
| 流畅度 | FPS、每帧耗时、Jank/BigJank、Game/Render/RHI 线程 | 平均、P95、P99、低帧占比、最长连续低帧 |
| CPU | 进程/整机利用率、核心频率、温度 | 峰值、持续高占用、降频时刻 |
| GPU | 利用率、频率、显存、温度 | 峰值、持续饱和、显存增长 |
| 内存 | PSS、堆、原生堆、Swap | 峰值、增长斜率、退出场景后的回收率 |
| 功耗 | 电流、电压、电池温度、容量 | 平均功率、单位时间耗电、温升 |
| 加载 | 启动/场景/资源阶段时间 | P50/P95、最长阶段、相对基线回退 |
| 网络/磁盘 | 发送/接收字节、包、读写量 | 平均/峰值速率、累计流量、突刺 |
| 渲染 | triangles、draw calls、mesh calls、粒子数 | 热区最大值、与低帧时间相关性 |

Jank 定义必须跟工具一起记录。若项目用帧预算倍数，可约定帧时间超过 `2×预算` 为 Jank、超过 `3×预算`
为 BigJank；如果采集器有自己的定义，以工具文档为准，不能混用。

### 9.3 实验室参考门槛

| 目标 | 平均 FPS 示例 | P95 帧时间示例 | P99 帧时间示例 |
| --- | --- | --- | --- |
| 60 FPS | ≥55 | ≤20 ms | ≤33.3 ms |
| 30 FPS | ≥28 | ≤40 ms | ≤66.7 ms |

其他练习值：重复场景并完成可比的回收操作后，PSS 增长不超过基线的 `5%～10%` 且没有线性上升；
预热后持续运行的 FPS 相对冷态下降不超过 10%；相同条件下新版本 FPS 回退不超过 5%、加载/内存回退不超过 10%。
这些值只适合先搭实验室门禁，最终应分设备档位和场景设预算。

CPU 持续超过 80%、GPU 持续超过 90% 是定位信号，不应单独判失败；满 GPU 也可能是正常充分利用。
温度优先看 OS thermal state 和是否降频，不跨机型比较一个绝对温度。实验室可把电池 `42～45°C` 作为关注区间，
但设备安全规范和厂商状态优先；不能为了过测试绕过设备保护。

发布阻断场景中 Crash、ANR、OOM 为 0。线上 Crash-free session 可设如 `≥99.9%` 的 SLO，但只有足够真实样本时才有意义。

### 9.4 本项目场景热力图设计

后续自行实现的采样格式至少应包含：

```text
Location, Rotation, FPS, RHITriangles, RHIDrawPrimitiveCalls,
MeshDrawCalls, NiagaraNumParticles, NiagaraNumMeshVerts
```

同一位置可按多个朝向聚合 P1 FPS、P95 帧时间、最大 triangles 和最大 draw calls，再把低帧与渲染负载映射回
地图格子，用于检查遮挡、LOD、粒子和材质。实现时必须保留原始样本与 hash，记录每点样本数、缺失点比例、
单位、设备和基线版本；颜色只用于展示，真正门禁必须来自本项目按设备档位和场景制定的预算。

### 9.5 稳定性与泄漏

覆盖长时间挂机/战斗、场景反复进入退出、登录登出、资源下载、前后台、锁屏、来电、低内存、存储满和网络切换。
记录每轮开始/结束内存、句柄/线程/对象数量、GC、温度、Crash/ANR/OOM 和最后一个成功步骤。

判断泄漏应看多轮后的增长斜率和退出场景后的回收，而不是只看一次峰值。实验室循环必须 0 Crash/ANR/OOM；
线程、句柄和内存不能随轮次持续单调增长。绝对内存上限按最低目标设备预算设置。

**面试回答重点**：我会先保证场景可重复和采样口径一致，再用 P95/P99、增长斜率和基线回退定位，而不是只报平均 FPS。

## 10. 配置表、数值表、Excel/CSV 与 Lua

### 10.1 推荐的数值 Schema 表头

业务数据表和字段规则表应分离。字段规则表可以使用：

```text
field_name, display_name, type, required, default,
min, max, boundary, enum, unique,
foreign_table, foreign_field, precision, description
```

常见业务数据列可以是：

```text
id, name, level, min_value, max_value, probability,
start_time, end_time, version, enabled, remark
```

项目可用中文表头，但生成器内部应映射为稳定字段名，并给模板加 `schema_version`。不要依靠“第 4 列永远是概率”这类脆弱约定。

### 10.2 必查规则与上下限

| 规则 | 示例 |
| --- | --- |
| 类型/空值 | int、float、string、bool、enum；required 不能空 |
| 主键 | ID > 0、唯一、稳定；重复和空 ID 为 0 |
| 最小/最大 | 明确包含/不包含；测试 min±1、max±1 |
| 概率 | 统一使用 `[0,1]` 或 `[0,100]`；同一概率池合计为 1 或 100，允许误差需声明 |
| 范围 | `min_value ≤ max_value`，数量/价格非负，容量不溢出 |
| 时间 | `start_time < end_time`，禁止意外重叠，明确时区 |
| 外键 | 引用目标必须存在；删除/版本变化后仍保持一致 |
| 跨表 | 等级/经验单调、解锁链可达、配方闭合、无禁止的循环依赖 |
| 精度 | 金额用整数最小货币单位；浮点误差 epsilon 由领域声明 |
| 存储极值 | 根据实际类型验证，如 signed int32 最大 `2,147,483,647` |

还要测空行、隐藏列、合并单元格、重复表头、额外列、公式、特殊字符、科学计数法、超大文件和旧模板版本。

### 10.3 Excel/CSV 到 Lua 的正确流水线

```text
工作簿/CSV
  → 文件类型、大小、hash、模板版本检查
  → 精确表头、类型、空值、范围、唯一、外键和跨表规则
  → 生成规范化中间模型
  → 按稳定主键排序
  → 确定性生成 Lua
  → Lua 转义、数字区域设置和 nil 策略检查
  → 隔离 Lua 运行时做语法/加载测试
  → 可选的反序列化对账
  → 生成 manifest、版本、hash 和差异报告
  → CI 审批后发布制品
```

“确定性”意味着相同输入必得字节完全相同的输出：排序稳定，换行固定，小数点不受系统语言影响，字符串正确转义，
时间和布尔值规则唯一。不要在生成阶段执行表格公式或不可信 Lua。

### 10.4 当前项目实现边界

当前学习平台已经实现版本化 CSV/XLSX 模板、预检、SHA-256、逐行错误、拒绝公式、提交和导出，但尚未实现
完整数值 Schema、跨表规则和 Lua 生成器。因此应准确表述为“已实现表格安全导入，并设计了 Lua 生成链路”，
除非后续真正把确定性生成器、Lua 加载测试、反向对账和 CI 制品做完。

## 11. 测试用例、缺陷、附件、审计和报表

### 11.1 用例设计与归档

用例最少包含标题、优先级、前置条件、步骤、期望、数据、环境和标签。步骤要原子、期望可观察；
版本发布时创建不可变快照，避免后来编辑源用例导致历史执行失真。

覆盖率不能只用“用例数量”表示，可以同时报告：

- 需求覆盖率 = 有关联用例的需求 / 总需求；
- 自动化覆盖率 = 自动执行用例 / 可自动化用例；
- 执行触达率 = 本轮已执行用例 / 计划用例；
- 风险覆盖率 = 已覆盖风险权重 / 总风险权重。

### 11.2 缺陷单和审计

高质量缺陷应含：环境/构建、前置、最小复现步骤、期望/实际、复现率、严重程度、日志、截图/视频、
request_id、关联用例和影响范围。严重程度回答影响，优先级回答处理速度。

状态流转、负责人、评论、附件和字段修改应保留追加式审计。发布前通常要求 blocker/critical 未关闭数为 0；
其他级别的接受必须有风险责任人和延期理由。审计记录不等于合规审计，若无签名、不可篡改存储、保留策略和职责分离，
面试中不要宣称合规级能力。

### 11.3 Excel/CSV 批量导入

推荐流程是“下载版本化模板 → 本地填写 → 只读预检 → 展示逐行错误和文件 hash → 用户确认提交 → 审计 → 导出核对”。
预检不得产生业务数据；提交应使用同一 hash 防止文件被替换。表头、类型、唯一键、引用、文件大小、行数和公式策略都应校验。

## 12. 冒烟、回归、发布与线上观察

### 12.1 冒烟测试

冒烟只覆盖版本是否值得继续测试：安装/启动、登录、进入核心玩法、关键 UI、一次核心业务闭环和退出。
冒烟用例应少而稳定，主链路通过率通常要求 100%；任一 blocker 直接退包。

### 12.2 回归测试

回归范围由“改动代码/配置 → 公共依赖 → 业务调用者 → 历史缺陷 → 高风险主链路”推导。
分为修复点验证、直接影响回归、公共模块回归和全量回归；不是每次都盲跑全部用例。

实验室门禁可先设：关键用例 100% 通过、总回归通过率 ≥95%～98%、新增 blocker/critical 为 0、
自动化 flaky rate <1%～2%。这些是起步值，不能用提高总通过率来掩盖关键用例失败。

### 12.3 发布验收和监控

发布前检查包体/签名/hash、配置和数据库兼容、回滚方案、已知问题、审批、测试报告和监控看板。
发布后观察登录成功率、Crash/ANR、错误码、接口 P95/P99、付费/匹配/结算成功率和资源下载失败。

阈值应结合绝对 SLO 与相对基线；告警必须有持续时间和最小样本，避免一条请求造成假警报。

## 13. 自动化、CI/CD、Jenkins、GitLab CI 与蓝盾

### 13.1 什么适合自动化

优先自动化稳定、频繁、可判定、数据可重置的 API、配置检查、冒烟和主回归；探索性、主观画面和快速变化功能保留人工。
分层顺序通常是单元/规则校验 → API/服务集成 → 少量 UI 主链路 → 设备/场景专项。

自动化结果必须包含输入版本、环境、原始日志、失败截图、重试前结果和稳定复现方式。失败后无脑重跑会掩盖 flaky。

### 13.2 QA 流水线

```text
提交/合并请求
  → 静态检查与单元测试
  → 构建、签名和制品 hash
  → API/集成测试
  → 冒烟与关键回归
  → 配置表/Lua 校验
  → 性能和兼容专项（按计划或夜间）
  → 质量门禁与独立审批
  → 发布/回滚
  → 监控和报告归档
```

质量门禁可以组合：关键用例 100%、blocker/critical 为 0、覆盖率不下降、性能回退不超预算、配置检查全过、
制品 hash 一致。Pipeline 成功不是唯一发布依据，还要结合风险、监控和人工审批。

### 13.3 产品之间的关系

Jenkins、GitLab CI、GitHub Actions 和蓝盾都能编排流水线，但托管方式、权限、Runner/Agent、插件、制品和审批模型不同。
QA 平台通常不复制整个产品，而是通过 Provider 适配统一 `trigger/get/cancel`、状态、Artifact、Webhook 和审计。

当前学习网站包含 GitHub Actions 的仓库 CI、本机 Learning CI、统一 Provider、Webhook/轮询、幂等、审批、Artifact、
Outbox 和 Mock 契约；真实 Jenkins、GitLab 和蓝盾连接保持关闭。后续只能连接自己搭建的隔离实例，不能使用旧公司地址、
账号、数据库或 Token。

**面试回答重点**：我理解的不只是 YAML，而是触发幂等、异步状态机、Runner、制品、质量门禁、Secret、回调签名、
失败恢复和审计；供应商只是这些概念的不同实现。

## 14. 常见面试题答法

### 14.1 “你怎么确定测试覆盖够不够？”

> 我先按需求和事故风险拆功能、状态、数据、权限、网络、设备和版本兼容维度，再用用户量、变更范围和失败影响排序。
> 我报告的是需求/风险覆盖和执行触达，不只报用例数量；高风险路径必须有正向、异常、边界和恢复用例，发布后再用缺陷逃逸复盘补矩阵。

### 14.2 “性能阈值从哪里来？”

> 先用产品目标和最低设备确定帧预算、内存及加载预算，再在固定场景建立稳定基线，最后参考线上分位数。
> 我会写清设备、画质、构建、预热、时长和样本量，使用 P95/P99、低帧占比和增长斜率；CPU/GPU 高占用是定位信号，不单独当失败。

### 14.3 “怎么测弱网？”

> 我先建立基线，再分别注入带宽、延迟、抖动、丢包和断网，覆盖关键动作中切网、单向黑洞和恢复。
> 用请求 ID、序列号、抓包和前后数据快照对齐，最终检查超时提示、有限重试、重连收敛和幂等，尤其防止重复扣款和发奖。

### 14.4 “如何验证一张数值表？”

> 我不只检查单元格格式，而是用版本化 Schema 校验类型、空值、最小/最大、唯一、概率和、外键及跨表不变量。
> 然后生成确定性制品，做 Lua 语法/加载和可选反向对账，保存输入输出 hash 和 diff，最后放进 CI 门禁。

### 14.5 “兼容测试是不是多找几台手机点一遍？”

> 不是。我根据真实用户占比和高风险芯片/OS/分辨率/图形 API 选矩阵，固定图形场景采集截图、日志和性能，
> 同时测安装升级、权限、前后台和降级。关键崩溃/黑屏零容忍，轻微视觉差异才使用带 mask 的项目阈值。

### 14.6 “发现 FPS 降低怎么定位？”

> 先确认场景、设备、温度、画质和构建可比，再看帧时间 P95/P99 与 CPU/GPU 饱和，按 Game/Render/RHI 线程判断瓶颈。
> 然后把低帧时间戳映射到场景位置，关联 triangles、draw calls、粒子、资源加载和温度降频，最后用单变量实验验证原因。

### 14.7 “你做过 CI/CD 吗？”

> 我做过 QA 平台侧的流水线模型：测试门禁、触发幂等、异步查询、签名 Webhook、乱序去重、审批、Artifact 和失败恢复。
> 当前真实 Jenkins/GitLab/蓝盾保持关闭，我使用本机实验室和 Mock 契约验证；因此我会区分已实现能力与尚未真实联调的部分。

### 14.8 “怎样写一个好缺陷？”

> 我会提供最小复现、构建和环境、复现率、期望/实际、影响、日志/视频、请求 ID 和关联用例；严重程度与优先级分开。
> 修复后先验证根因，再回归公共依赖和相邻状态，并保留审计和版本证据。

## 15. 面试前速查清单

### 测试设计

- 能否说清目标、最大风险和覆盖矩阵？
- 是否覆盖正常、异常、边界、并发、中断和恢复？
- 是否准备可复现账号、数据、环境和清理方案？

### 数据和阈值

- 指标是否有单位、公式、采样周期、分位数和样本量？
- 阈值属于硬约束、项目预算还是实验室示例？
- 是否保存原始数据、版本、设备和时间戳？
- 是否同时比较绝对上限与相对基线？

### 缺陷和发布

- 缺陷能否由别人独立复现并快速定位？
- 修复点、直接影响、公共依赖和历史问题是否回归？
- blocker/critical、关键用例、性能回退和回滚方案是否满足门禁？

### 真实性边界

- **已经实现**：可以讲代码、测试和验证结果；
- **只做过源码审计**：讲发现、证据、缺口和改进设计；
- **只做过方案设计**：明确说“设计过/计划实现”，不要说“已经落地”；
- **模拟环境**：说明自建隔离服务、Mock 和真实产品契约之间的差异。

## 16. 本项目继续学习的推荐顺序

1. 用现有用例、缺陷、评论、附件、审计和 Excel/CSV 模块走通功能测试闭环；
2. 用本机异步 HTTP 与 Learning CI 练习超时、重试、幂等、轮询和 Webhook；
3. 新增配置 Schema 校验和确定性 Excel/CSV → Lua 生成器；
4. 新增可控网络 Profile、协议时间线和断网恢复测试；
5. 新增本机性能采集格式、场景轨迹热力图和基线比较；
6. 新增带设备元数据、基线、mask、diff 和人工审批的图形兼容报告；
7. 最后连接自己搭建的 Jenkins/GitLab/蓝盾实验室，完成制品、质量门禁和回滚演练。
